# Executing a plan on Pi

Use `pi-peer-sessions` when authorized delegation materially helps an existing
plan. Pi collaborators are ordinary independent sessions, not native child runs.
Keep serial or tightly coupled tasks in the requesting session.

Give each peer a bounded component or review and the context it needs. Concurrent
writers use distinct Git worktrees or jj workspaces; do not run checks against a
checkout another session is changing. Keep ownership and prerequisites in the
existing plan and todos, not a second lane board or shared scheduler.

Communicate through Intercom. Each session runs its normal profile and auto
permissions. The requester checks returned evidence and integrates accepted
work; this is result verification, not permission approval. Each peer maintains
its own detailed task list. Record the outstanding dependency and source state
in the requesting session, and retain report paths when a larger handoff needs
them.

Use the implementer and reviewer templates as task content, not native tool-call
syntax. Follow the plan's required review and integration gates. When no suitable
peer terminal exists, work directly; report any required independent review as
outstanding rather than pretending a self-review satisfies it.
